# 심화 요구사항

[README](../README.md) · [필수 요구사항](requirements.md) · [진행 기록과 발표](project-guide.md)

[필수 요구사항](requirements.md)을 먼저 완성한 뒤 관심 있는 과제를 선택하세요. 모두 구현할 필요는 없고, 하지 않아도 필수 기능과 검증 결과만으로 발표할 수 있습니다. 처음 보는 용어는 그 과제를 선택했을 때 읽으면 됩니다.

| 심화 과제 | 시작하기 좋은 시점 | 난이도 |
|---|---|---|
| 1. 한 파일 처리 시간 개선 | 큰 데이터 처리와 시간 측정 후 | 중 |
| 2. 여러 파일 병렬 처리 | 순차 처리 결과를 검증한 후 | 중~상 |
| 3. 파일 단위 중단 후 재개 | 파일별 결과를 분리한 후 | 중 |
| 4. 큰 파일 내부 중단 후 재개 | 3번을 검증한 후 | 상 |
| 5. 직접 데이터 수집 | 필수 기능 전체 완성 후 | 중 |
| 6. 분석 기능 확장 | 기본 카운팅과 저장 완성 후 | 하~중 |
| 7. 데이터베이스에 저장하며 집계 | 필수 기능 전체 완성 후. Docker 권장, H2로 대체 가능 | 상 |
| 8. 객체지향 구조 개선 | 네 형식이 모두 동작한 후. 다른 심화보다 먼저 해도 좋음 | 중 |

## 성능 실습 데이터

실제 뉴스 제목 45,678건을 8번 반복한 부하 실험용 입력입니다. 읽기, 파싱, 집계 작업량은 늘어나지만 단어 종류는 늘어나지 않습니다. CSV 열은 `text`이고, 두 입력은 [같은 정답](../expected/news-repeat-8-counts.tsv)을 사용하며 한꺼번에 합산하지 않습니다.

| 입력 | 건수 / 파일 수 | 크기 | 전체 단어 수 | 종류 수 |
|---|---|---|---:|---:|
| `data/performance/news-repeat-8.csv` | 365,424 / 1 | 약 27.3MB | 2,568,672 | 78,309 |
| `data/performance/many` | 365,424 / 16 | 합계 약 27.3MB | 2,568,672 | 78,309 |

스레드는 프로그램 안에서 동시에 진행되는 작업 흐름 하나입니다. 스레드 하나로 파일을 차례대로 처리하는 것이 순차 처리이고, 여러 스레드로 여러 파일을 동시에 처리하는 것이 병렬 처리입니다. 진행 방향은 **한 파일의 카운팅을 정확하게 → 한 파일의 처리 시간 개선(1번) → 여러 파일의 전체 처리 시간 개선(2번)** 순서입니다. 큰 파일 하나를 여러 스레드로 쪼개는 구현은 2번 뒤의 추가 도전입니다. 더 큰 입력이 필요하면 1번 끝의 생성 도구로 로컬에 만들 수 있습니다.

## 측정 방법 (1번·2번 공통)

**JVM**은 Java 프로그램을 실행하는 환경이고, 처음 실행할 때의 준비·최적화 영향을 줄이려고 먼저 한 번 돌려보는 것을 **예열**이라고 합니다. **중앙값**은 측정값을 정렬했을 때 가운데 값으로, 120ms, 90ms, 100ms의 중앙값은 100ms입니다.

1. 같은 기기, JDK, 입력, 분석 설정을 사용합니다. 원문 출력이나 진행 로그 조건도 같게 합니다.
2. 측정 구간은 필수 요구사항의 처리 시간과 같습니다. 파일 읽기부터 모든 결과 합산 완료까지이며 정렬·저장은 제외합니다.
3. 가능하면 같은 프로그램 실행 안에서 예열 1회 후 3회 이상 측정합니다. 메뉴의 새 분석을 반복하고 매번 이전 집계는 초기화합니다. 매번 Run을 다시 눌러 측정했다면 그 방식을 기록합니다.
4. 중앙값을 기록하고 **전체 단어별 횟수**를 비교합니다. 상위 10개가 같은 것만으로 검증하면 안 됩니다. 예열 1회로 모든 영향이 사라지지는 않으므로 작은 차이를 단정하지 마세요.

## 1. 한 파일 처리 시간 개선

스레드 하나로 `news-repeat-8.csv`를 처리하면서 비용이 큰 부분을 찾아 바꿉니다. **바꾸기 전에 시간을 나눠 측정하고, 가장 큰 부분부터 바꾸세요.** 모든 항목을 적용할 필요는 없습니다.

먼저 같은 파일을 세 가지 범위로 처리해 시간이 어디에 쓰이는지 나눠 봅니다. (가) 파일을 읽어 CSV 레코드에서 `text` 셀을 꺼내기만 하기, (나) 거기에 단어 분리까지, (다) 거기에 집계까지(지금 프로그램). 코드에서 단어 분리와 집계 부분을 잠시 빈 처리로 바꾸거나 주석 처리해 각각 재면 됩니다. 참고 구현에서는 (가)가 약 17%, 단어 분리가 약 50%, 집계가 약 30%였습니다. 여러분의 구현에서는 비율이 다를 수 있으니 직접 측정한 값을 기록하세요.

| 시도 | 내용 | 참고 구현 효과 |
|---|---|---|
| 단어 분리를 정규식에서 문자 검사로 | 문자열을 한 글자씩 보며 허용 문자 구간을 직접 잘라냄. 결과가 정규식과 같은지 확인 | 전체 시간 약 40% 감소 |
| 집계 자료구조 확인 | `TreeMap`으로 집계하고 있었다면 `HashMap`으로 바꾸고, 정렬은 조회·저장할 때만 | 약 33% 감소 |
| 목록 검색 집계 | `List`에서 단어를 찾아 세고 있었다면 `Map`으로 | 약 170배 빨라짐(27.3MB에서 83초 → 0.5초) |
| 토큰마다 출력 제거 | 디버그용 출력이 남아 있으면 처리 시간의 대부분이 출력에 쓰임 | 7배 이상 빨라짐. IntelliJ 콘솔이면 더 큼 |

효과가 거의 없는 것도 있습니다. 정규식 `Pattern`을 줄마다 새로 만들던 것을 재사용하기, 파일 전체를 읽던 것을 줄별 처리로 바꾸기, `HashMap` 초기 용량 지정은 측정마다 0~20% 사이로 흔들려 효과를 단정하기 어려웠습니다. **바꾸기 전에 효과를 예상하고 측정으로 확인하는 것**이 이 과제의 목적이므로, 효과가 없다는 결론도 이유와 함께 기록할 가치가 있습니다.

| 버전 | 입력 | 1회(ms) | 2회(ms) | 3회(ms) | 중앙값(ms) | 전체 결과 동일 |
|---|---|---|---|---|---|---|
| 개선 전 | `data/performance/news-repeat-8.csv` |  |  |  |  |  |
| 개선 후 | 같은 파일 |  |  |  |  |  |

**완료 기준**: 바꾼 코드와 이유, 측정 조건과 결과를 `PROGRESS.md`에 적습니다. 시간이 줄지 않아도 가능한 원인을 설명하면 의미 있는 실험입니다. 메모리를 비교했다면 측정 도구와 Java 실행 옵션을 기록하고 순간 사용량과 최대 사용량을 구분하세요. 메모리를 줄이는 변경이 항상 시간을 줄이지는 않습니다.

### 더 큰 파일로 체감하려면 (선택)

27.3MB에서는 40% 개선이 200ms 차이라 숫자로만 보입니다. 초 단위로 느껴보고 싶다면 `news-full.csv`를 반복한 큰 파일을 로컬에 만들 수 있습니다. 프로젝트 루트에서 실행하며, 생성 위치 `data/local`은 Git에 올라가지 않습니다.

```sh
java tools/RepeatCsv.java
```

`java` 명령은 JDK 21의 것이어야 합니다. `java -version`으로 확인하고, IntelliJ 하단의 Terminal에서 실행해도 됩니다. 기본값은 64번 반복·16개 분할로, `data/local/perf-64/news-repeat-64.csv`(약 215MB, 2,923,392건)와 같은 내용을 16개로 나눈 `data/local/perf-64/many/`가 만들어집니다. 두 입력의 정답은 **전체 단어 20,549,376개, 종류 78,309개**로 같습니다. 정답 파일은 따로 없으니 두 입력의 저장 결과가 서로 같은지와 종류 수로 확인하세요. 반복 횟수와 분할 수는 인수로 바꿀 수 있습니다. 예: `java tools/RepeatCsv.java 32 8`

참고 구현에서는 이 파일이 순차 약 4초, 단어 분리를 문자 검사로 바꾸면 약 2초, `TreeMap` 집계는 약 6초였습니다. 파일이 커지면 전체를 한 번에 읽는 방식과 레코드별 처리의 메모리 차이도 관찰할 수 있습니다.

## 2. 여러 파일 병렬 처리

목표는 **16개 파일을 모두 카운팅하고 결과를 합칠 때까지 걸리는 시간**을 줄이는 것입니다. 파일 하나의 시간만 재거나 파일별 시간을 더해 전체 시간으로 기록하지 마세요.

```text
순차 처리: 파일 1 → 파일 2 → ... → 파일 16 → 합산 완료

작업 스레드 4개:
  작업자 1 ┐
  작업자 2 ├─ 16개 파일을 나누어 처리 → 모두 완료 대기 → 성공 결과 합산
  작업자 3 │
  작업자 4 ┘
```

1. `data/performance/many`의 CSV 16개를 스레드 하나로 처리한 결과와 시간을 기준으로 보관합니다.
2. 작업 스레드 수를 2개, 4개로 바꾸어 여러 파일을 동시에 처리합니다. 개수는 코드의 상수로 바꿔도 됩니다.
3. 각 파일은 자신의 집계용 `Map`을 사용하고, 성공한 파일의 결과만 합산합니다.
4. 모든 작업이 끝나고 합산까지 완료된 시점의 시간을 표시합니다.
5. 1·2·4개 스레드의 모든 단어별 횟수가 같은지, [정답](../expected/news-repeat-8-counts.tsv)과도 같은지 확인합니다.

| 입력 폴더 | 스레드 수 | 파일 수 | 1회(ms) | 2회(ms) | 3회(ms) | 중앙값(ms) | 전체 결과 동일 |
|---|---:|---:|---|---|---|---|---|
| `data/performance/many` | 1 | 16 |  |  |  |  |  |
| 같은 폴더 | 2 | 16 |  |  |  |  |  |
| 같은 폴더 | 4 | 16 |  |  |  |  |  |

- `Thread.start()`·`join()`으로 구현하거나 `ExecutorService`의 고정 크기 스레드 풀을 사용할 수 있습니다. 스레드 풀은 정해진 수의 작업 스레드가 여러 작업을 나누어 맡도록 관리하고, `join()`은 그 스레드의 완료를 기다립니다. `ExecutorService`는 작업이 끝나면 `shutdown()`으로 종료하세요. [Java Executors 공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html)
- 같은 `HashMap`을 여러 스레드에서 동시에 수정하면 갱신이 누락될 수 있습니다. 파일별로 따로 집계하고 합치는 방식부터 시작하세요.
- 파일 수만큼 스레드를 만들 필요는 없습니다. 디스크 속도, 작업 준비, 합산 비용 때문에 스레드를 늘려도 빨라지지 않을 수 있습니다.
- 단일 파일의 시간과 16개 파일의 시간을 바로 비교해 병렬 처리 효과라고 판단하지 마세요. **같은 16개 파일을 순차·병렬로 처리한 시간끼리** 비교합니다.
- 더 큰 폴더로 비교하려면 1번 끝의 생성 도구로 만든 `data/local/perf-64/many`(16개 파일, 합계 약 215MB)를 사용하세요. 참고 구현에서 순차 약 4초 → 스레드 4개 약 1.2초였습니다. `java tools/RepeatCsv.java 64 64`처럼 분할 수를 바꾸면 파일 64개로도 비교할 수 있습니다.

**완료 기준**: 실행 순서와 스레드 수에 관계없이 결과가 같고, 실패 파일은 제외되며, 전체 작업이 정상적으로 끝나야 합니다. 오류 파일을 추가한 별도 폴더에서도 확인하세요. 측정 표와 관찰한 이유를 `PROGRESS.md`에 남깁니다.

**그다음 도전**: 큰 파일 하나를 파싱한 레코드 묶음으로 나누어 병렬 처리합니다. 대기 묶음 수를 제한해 메모리가 계속 늘어나지 않게 하세요. CSV 파일의 실제 줄(줄바꿈 기준)이나 UTF-8 바이트를 임의로 나누면 셀이나 한글이 끊길 수 있습니다.

## 3. 파일 단위 중단 후 재개

체크포인트는 작업 도중 저장해두는 진행 상태입니다. 프로그램을 다시 실행했을 때 그 상태를 읽어 이어서 처리합니다.

```text
a.txt 완료 → a.txt의 결과 저장
b.csv 완료 → b.csv의 결과 저장
c.html 처리 도중 프로세스 종료

다시 실행:
a.txt·b.csv의 저장된 결과 복원 → c.html은 처음부터 처리
```

- 완료 파일 목록과 **완료한 파일의 단어별 결과**를 함께 저장합니다. 파일 이름만 저장하면 재실행 후 이전 집계를 복원할 수 없습니다. 저장된 결과를 두 번 더하지 않도록 합산 방법도 정하세요.
- 파일 경로만으로 변경을 판단하지 마세요. SHA-256 같은 해시(파일 내용에서 계산한 요약값)를 저장해두고 재실행 시점의 값과 비교하면 내용이 바뀌었는지 알 수 있습니다. Java의 `MessageDigest`를 사용할 수 있으며, 분석 실행 중에는 입력이 바뀌지 않는다고 가정해도 됩니다.

**완료 기준**: 두 개 이상 파일이 있는 작업을 도중에 종료한 뒤 재실행할 수 있고, 완료 파일은 다시 집계하지 않으며 미완료 파일은 다시 처리합니다. 최종 결과가 중단 없이 실행한 결과와 같고, 원본 파일이나 분석 설정이 바뀌면 저장 상태를 재사용하지 않고 이유를 안내합니다.

## 4. 큰 파일 내부 중단 후 재개

3번을 완성한 뒤 큰 TXT 또는 TSV 하나를 대상으로 확장합니다. 처음에는 단일 스레드로 구현해도 되고, HTML 파일 중간부터 이어 가는 기능은 만들지 않아도 됩니다.

데이터 레코드 1,000개마다 다음 상태를 한 묶음으로 저장합니다. TXT는 파일의 실제 줄(줄바꿈 기준)을 레코드로 삼아도 되고, CSV·TSV는 헤더를 제외한 데이터 레코드 번호를 사용합니다. 빈 셀이라 단어를 추가하지 않은 레코드도 처리 위치에는 반영하며, CSV에서 여러 줄에 걸친 값은 레코드 하나입니다.

| 저장 항목 | 의미 |
|---|---|
| 작업·입력 정보 | 대상 파일과 내용 식별 정보(해시) |
| 처리 완료 위치 | 집계에 반영된 마지막 레코드 번호 |
| 집계 상태 | 그 위치까지의 단어별 누적 횟수 |
| 분석 설정 | 형식, 분석 열, 단어 규칙 버전, 불용어 등 |

- 재실행하면 **마지막으로 정상 저장한 지점 다음부터** 이어갑니다. 저장하지 못한 구간은 다시 처리해도 됩니다. 단, 저장된 위치와 횟수는 같은 시점의 상태여야 합니다. 처음에는 파일 처음부터 다시 읽으며 완료한 레코드를 건너뛰어도 됩니다.
- 종료 시점에만 저장하지 말고 실행 중 일정 간격으로 저장합니다. 강제 종료에서는 종료 처리 코드가 실행되지 않을 수 있습니다.
- 새 상태는 임시 파일에 완성한 뒤 확정하고, 이전에 정상 저장한 파일은 남겨 둡니다. 저장 도중 종료되어도 불완전한 상태를 읽으면 안 됩니다. `Files.move`의 `ATOMIC_MOVE`를 쓸 수 있지만 지원하지 않는 환경도 있으니 대비하세요. [Java Files 공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...))
- 필수 요구사항의 실패 파일 제외 규칙을 유지합니다. 완료되지 않은 파일의 부분 결과는 최종 성공 합계로 확정하지 않습니다.

**검증 순서**: 중단 없이 처리한 전체 결과를 보관 → 처리 도중 Java 프로세스를 종료(방법 기록) → 재실행해 복원 위치 확인 → 끝까지 처리한 결과를 보관본과 비교 → 저장 중 종료, 파일 내용 변경, 설정 변경도 확인. `ProcessHandle.current().pid()`로 실험용 프로세스의 PID를 출력해두면 작업 관리자나 활성 상태 보기에서 종료할 대상을 찾기 쉽습니다. IDE의 Stop 버튼만 사용했다면 종료 처리 코드가 실행되는 방식인지도 확인해 기록합니다. 저장 주기를 짧게 하면 재작업 구간은 줄고 저장 비용은 늘어나는데, 그 차이를 측정해볼 수도 있습니다.

## 7. 데이터베이스에 저장하며 집계

메모리의 `Map` 대신 **데이터베이스(DB) 표에 단어별 횟수를 저장하며** 카운팅합니다. 같은 일을 DB로 하면 처음에는 수백 배 이상 느려집니다. 느려지는 원인을 단계별로 없애 가면서 트랜잭션, 배치, "계산은 어디서 하는가"를 배우는 과제입니다. 수업에서 DB를 배우기 전이므로 아래 용어와 SQL 다섯 문장만 사용합니다. 필수 기능은 그대로 두고, 저장과 조회를 DB로도 할 수 있게 확장하세요.

### 용어

| 용어 | 이 과제에서의 뜻 |
|---|---|
| 데이터베이스(DB), MySQL | 데이터를 표 형태로 저장하고 조회하는 프로그램. 이 과제에서는 MySQL 8.4를 사용 |
| 표, 행, 열 | 표는 열이 정해진 데이터 묶음, 행은 데이터 한 건(CSV의 레코드와 같음), 열은 항목 |
| SQL | 표를 만들고 읽고 쓰는 명령 언어. `SELECT`(읽기), `INSERT`(행 추가), `UPDATE`(수정) |
| JDBC, 드라이버 | Java에서 SQL을 보내는 표준 방법, 그 명령을 MySQL에 전달하는 라이브러리 |
| 왕복 | Java가 SQL 한 문장을 보내고 결과를 받는 데 걸리는 시간. 같은 컴퓨터 안에서도 약 0.1ms |
| 트랜잭션, 커밋, 자동 커밋 | 여러 변경을 한 묶음으로 확정하는 단위, 그 확정(디스크에 기록), 문장마다 자동으로 확정하는 기본 설정 |
| 배치 | 여러 문장을 모아 한 번에 보내는 것 |
| 기본 키, 인덱스 | 행을 하나로 식별하는 열(같은 값의 행이 둘일 수 없음), 찾기를 빠르게 하는 자료구조. 기본 키에는 인덱스가 자동으로 생김 |
| 정렬 규칙(collation) | 문자를 비교하고 정렬하는 규칙 |
| Docker, 이미지, 컨테이너 | 프로그램을 컴퓨터 안의 격리된 공간에서 설치 없이 실행하는 도구, 그 프로그램의 설치 파일 묶음, 실행 중인 한 개 |

### 준비

1. [Docker Desktop](https://www.docker.com/products/docker-desktop/)을 설치하고 실행합니다. Windows에서는 리눅스 실행 환경인 WSL2가 필요하며, [Windows 설치 안내](https://docs.docker.com/desktop/setup/install/windows-install/)의 순서를 따르면 함께 설정됩니다.
2. 프로젝트 루트에서 MySQL을 실행합니다. `-d`는 배경에서 계속 실행한다는 뜻이고, 처음 한 번은 이미지(약 200MB)를 다운로드합니다.

   ```sh
   docker compose -f tools/db/compose.yaml up -d
   ```

   `localhost:3307`에 데이터베이스 `wordcount`가 만들어지고(사용자와 비밀번호 모두 `wordcount`), `tools/db/init.sql`이 표 두 개를 만듭니다. 컴퓨터에 이미 설치된 MySQL과 충돌하지 않도록 3306 대신 3307을 씁니다. 10~20초 기다린 뒤 다음 명령으로 확인합니다. `db`는 `compose.yaml`에 적힌 서비스 이름입니다.

   ```sh
   docker compose -f tools/db/compose.yaml exec db mysql -uwordcount -pwordcount wordcount -e "SHOW TABLES;"
   ```

   `tokens`와 `word_counts` 두 줄이 나오면 됩니다. 앞에 붙는 `[Warning] Using a password ...`는 무시합니다.

   | 문제 | 확인할 것 |
   |---|---|
   | `Cannot connect to the Docker daemon` | Docker Desktop 앱이 실행 중인지 확인 |
   | `port is already allocated` | `compose.yaml`의 `"3307:3306"`에서 3307을 다른 번호로 바꾸고 연결 URL도 같이 변경 |
   | 표가 나오지 않음 | `init.sql`은 컨테이너를 처음 만들 때만 실행됩니다. `docker compose -f tools/db/compose.yaml down -v` 뒤 다시 `up -d` |

3. `pom.xml`의 `<dependencies>` 안에 MySQL 드라이버를 추가하고, Maven 도구 창(오른쪽 Maven 탭)에서 **Reload All Maven Projects**를 누릅니다.

   ```xml
   <dependency>
       <groupId>com.mysql</groupId>
       <artifactId>mysql-connector-j</artifactId>
       <version>9.3.0</version>
   </dependency>
   ```

4. 연결을 확인합니다. `Main`과 같은 패키지에 `DbCheck` 클래스를 만들어 `main`에 넣고 Run 하세요. `Connection`, `DriverManager`, `Statement`, `ResultSet`, `SQLException`은 모두 `java.sql` 패키지에 있고, `SQLException`은 처리하거나 `throws`로 넘겨야 하는 예외입니다.

   ```java
   String url = "jdbc:mysql://localhost:3307/wordcount?rewriteBatchedStatements=true&allowPublicKeyRetrieval=true&useSSL=false";
   try (Connection connection = DriverManager.getConnection(url, "wordcount", "wordcount");
        Statement statement = connection.createStatement();
        ResultSet rs = statement.executeQuery("SELECT COUNT(*) FROM word_counts")) {
       rs.next();
       System.out.println("연결 성공. 저장된 단어 " + rs.getLong(1) + "개");
   }
   ```

   URL 뒤의 옵션 중 `rewriteBatchedStatements=true`는 배치를 한 문장으로 합쳐 보내는 설정이고, 나머지 둘은 같은 컴퓨터 안의 실습용 연결이라 암호화를 끄는 설정입니다.

   | 문제 | 확인할 것 |
   |---|---|
   | `No suitable driver found` | 3번의 의존성 추가와 Maven 새로고침 |
   | `Communications link failure` | 컨테이너가 실행 중인지(`docker ps`), 포트 번호가 URL과 같은지 |
   | `Access denied for user` | 사용자와 비밀번호가 `wordcount`인지 |

### 표

| 표 | 열 | 뜻 |
|---|---|---|
| `word_counts` | `word VARCHAR(255)` 기본 키, `count BIGINT` | 단어별 횟수. 기본 키라 같은 단어는 한 행만 존재. `VARCHAR`는 문자열, `BIGINT`는 Java의 `long` |
| `tokens` | `token VARCHAR(255)` | 6단계에서 집계 전의 토큰을 그대로 쌓아 두는 임시 표 |

두 표의 정렬 규칙은 `utf8mb4_bin`입니다. MySQL의 기본 규칙은 대소문자와 일부 비슷한 문자를 같은 것으로 취급해서, 그대로 두면 서로 다른 단어가 한 행으로 합쳐져 정답과 어긋납니다. `utf8mb4_bin`이면 정렬 순서도 Java의 `String.compareTo`와 같아져 정답 파일과 바로 비교할 수 있습니다.

### 이 과제에서 쓰는 SQL과 JDBC

SQL은 다음 다섯 문장이 전부입니다. `?` 자리에 Java에서 값을 넣습니다.

```sql
SELECT count FROM word_counts WHERE word = ?
INSERT INTO word_counts (word, count) VALUES (?, 1)
UPDATE word_counts SET count = count + 1 WHERE word = ?
INSERT INTO word_counts (word, count) VALUES (?, 1) ON DUPLICATE KEY UPDATE count = count + 1
INSERT INTO word_counts (word, count) VALUES (?, ?) ON DUPLICATE KEY UPDATE count = count + VALUES(count)
```

`ON DUPLICATE KEY UPDATE`는 같은 단어(기본 키)가 이미 있으면 추가 대신 뒤의 수정을 실행하라는 뜻입니다. 마지막 문장의 `VALUES(count)`는 "지금 넣으려던 행의 count 값"으로, 파일별로 집계한 횟수를 이미 있는 행에 더할 때 씁니다. 표를 비울 때는 `TRUNCATE TABLE word_counts`와 `TRUNCATE TABLE tokens`를 씁니다.

JDBC에서는 문장을 `PreparedStatement`로 준비하고 `?`에 값을 넣어 실행합니다. `?`의 번호는 1부터 시작합니다. 문자열을 이어 붙여 SQL을 만들지 마세요.

```java
connection.setAutoCommit(false);                 // 3단계부터: 문장마다 커밋하지 않음
try (PreparedStatement upsert = connection.prepareStatement(
        "INSERT INTO word_counts (word, count) VALUES (?, 1) ON DUPLICATE KEY UPDATE count = count + 1")) {
    for (String token : tokens) {
        upsert.setString(1, token);
        upsert.addBatch();                       // 4단계부터: 모아 두기. 1~3단계는 executeUpdate()
        if (++pending == 5000) {
            upsert.executeBatch();               // 모은 것을 한 번에 보내기
            pending = 0;
        }
    }
    upsert.executeBatch();                       // 남은 것 보내기
}
connection.commit();                             // 3단계부터: 마지막에 한 번 확정
```

### 단계

한 단계씩 구현하고 시간을 잰 뒤 다음 단계로 갑니다. 시간은 파일 읽기부터 마지막 `executeBatch()`와 `commit()`이 끝날 때까지입니다(측정 방법의 "저장은 제외"는 결과 파일 저장을 뜻합니다). 각 단계를 시작하기 전에 두 표를 `TRUNCATE`로 비웁니다.

**1·2단계는 `news-1000.csv`로만** 실행하세요. 27.3MB 파일로 하면 참고 구현에서 40~50분이 걸립니다. 대신 토큰 하나당 시간을 재서 257만 토큰이면 얼마나 걸릴지 **계산해** 기록하세요. 3단계도 27.3MB에서는 5분이 넘습니다(참고 구현 5분 5초).

| 단계 | 방식 | 재는 파일 | 배우는 것 | 참고 구현(두 번 측정한 범위) |
|---|---|---|---|---|
| 1 | 토큰마다 `SELECT`로 있는지 확인한 뒤 `INSERT` 또는 `UPDATE`. 자동 커밋 | news-1000 | 왕복 2회에 커밋까지, 토큰마다 약 1ms | 7~8초(메모리 약 0.02초) |
| 2 | 토큰마다 `INSERT ... ON DUPLICATE KEY UPDATE` 한 문장. 자동 커밋 | news-1000 | 왕복 2회를 1회로 | 5.6~6.4초 |
| 3 | 2와 같지만 `setAutoCommit(false)`로 시작해 마지막에 `commit()` 한 번 | news-1000, news-10000 | 커밋마다 디스크에 기록하던 비용 제거. 남는 것은 왕복 | 0.7초, 8초 |
| 4 | 3과 같지만 `addBatch()`로 모아 5,000개마다 `executeBatch()` | news-10000, 27.3MB | 왕복 횟수 자체를 줄이기 | 0.35초, 15초 |
| 5 | 파일을 메모리 `Map`으로 먼저 집계한 뒤, 단어별로 한 번씩 `VALUES(count)` 문장을 배치로 | 27.3MB | 계산은 싼 곳에서 하고 DB에는 결과만 저장 | 0.4\~0.6초(메모리만 0.3\~0.5초) |
| 6 (선택) | 토큰을 `tokens` 표에 배치로 쌓은 뒤 `INSERT INTO word_counts SELECT token, COUNT(*) FROM tokens GROUP BY token` | 27.3MB | 집계를 DB에 맡기면 어떻게 되는지 | 6~7초(저장 5초 + 집계 1초) |

조회 메뉴도 DB로 구현해보세요. 상위 N개는 `SELECT word, count FROM word_counts ORDER BY count DESC, word LIMIT ?`, 특정 단어는 `SELECT count FROM word_counts WHERE word = ?`입니다. 기본 키가 있는 열로 찾으면 빠르고, `ORDER BY count`는 인덱스가 없어 전체를 정렬하지만 78,309행이면 참고 구현에서 17ms였습니다.

### 검증

`SELECT word, count FROM word_counts ORDER BY count DESC, word`의 결과를 `word`, `count` 헤더와 함께 탭으로 구분한 파일로 저장하고, 기존 정답 파일과 Compare Files로 비교합니다. 순서까지 같아야 합니다. `ResultSet`을 한 행씩 읽어 `rs.getString(1)`과 `rs.getLong(2)`를 쓰면 되고, 필수 요구사항 7번의 저장 코드를 재사용할 수 있습니다. 새 분석을 시작할 때 표를 비우지 않으면 이전 결과에 누적되니, 필수 요구사항 1번의 "이전 결과에 더하지 않음" 규칙을 DB에서도 지키세요.

### 더 해보려면 (선택)

- 2번 병렬 처리와 결합: 여러 스레드가 동시에 같은 표에 쓰면 잠금 대기와 데드락(서로 상대의 잠금이 풀리기를 기다려 멈추는 상태)이 생길 수 있습니다. 스레드마다 먼저 집계한 뒤 한 스레드가 저장하는 방식과 비교하세요.

- 파일 수를 늘려 비교: `java tools/RepeatCsv.java 64 64`로 파일 64개를 만들어, 파일마다 커밋할 때와 전체를 한 번에 커밋할 때의 시간을 비교하세요.
- Docker 없이: [H2](https://www.h2database.com/) 같은 내장 DB(`com.h2database:h2`, URL `jdbc:h2:./data/local/wordcount`)로도 같은 실험을 할 수 있습니다. `INSERT ... ON DUPLICATE KEY UPDATE`에 해당하는 문법이 `MERGE INTO`로 다르고, 같은 프로세스 안에서 실행되어 왕복 비용은 작지만 커밋과 배치의 효과는 같은 모양으로 나타납니다.

## 8. 객체지향 구조 개선

기능과 정답은 그대로 두고 코드를 역할별 클래스로 나누는 과제입니다. 목표는 **새 형식을 추가할 때 파서 하나와 확장자를 등록하는 곳 하나만 바꾸면 되는 구조**입니다. 네 형식이 모두 정답을 내는 상태에서 시작하고, 바꾼 뒤에는 검증 방법 전체를 다시 돌려 결과가 같은지 확인합니다.

나눠볼 역할의 한 예입니다. 이름과 개수는 자유입니다.

| 역할 | 하는 일 | 알 필요가 없는 것 |
|---|---|---|
| 형식별 파서 | 파일에서 분석할 텍스트 조각을 꺼냄. TXT·CSV·TSV·HTML마다 한 클래스, 모두 같은 인터페이스 | 단어 규칙, 집계, 메뉴 |
| 단어 처리 규칙 | 텍스트를 토큰으로 나누고 소문자·숫자 규칙을 적용 | 파일 형식 |
| 단어별 집계 | 토큰을 세고, 파일별 결과를 합치고, 정렬 | 파일, 콘솔 |
| 분석 | 입력 경로에서 파일 목록을 만들고, 파일마다 파서를 골라 집계하고, 성공한 결과를 합산하고, 시간을 잼 | 콘솔 문구 |
| 결과 저장 | 집계를 TSV로 씀 | 어떻게 집계했는지 |
| 콘솔 메뉴 | 입력을 받고 위 역할들을 호출하고 결과를 보여줌 | 파일 형식별 처리 방법 |

인터페이스는 서로 다른 파서를 같은 메서드 약속으로 다루는 방법입니다. 파서 인터페이스에 "파일을 받아 텍스트 조각을 넘긴다"는 메서드 하나만 두면, 분석 역할은 어떤 형식인지 몰라도 같은 코드로 모든 파일을 처리할 수 있습니다.

구조가 잘 나뉘었는지 확인하는 질문입니다.

- 콘솔 메뉴 코드에 `.csv`, `#content` 같은 파일 형식 이름이 나오지 않나요?
- 6번 표의 JSON처럼 새 형식을 하나 추가하면, 바뀌는 파일이 새 파서 하나와 확장자를 등록하는 곳 하나뿐인가요?
- 2번 병렬 처리를 붙일 때 "파일 하나를 처리해 집계를 돌려주는" 코드를 고치지 않고 그대로 여러 스레드에서 부를 수 있나요?
- 7번처럼 저장 위치를 DB로 바꿀 때 파서와 집계 코드는 그대로인가요?

**완료 기준**: 클래스별 역할을 한 줄씩, 새 형식을 추가할 때 바꾸는 곳, 바꾸기 전과 후의 검증 결과가 같다는 확인을 `PROGRESS.md`에 적습니다. 발표에서는 어떤 역할을 나눴고 왜 그렇게 나눴는지 설명하세요.
